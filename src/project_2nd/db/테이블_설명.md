# DB 테이블 상세 설명

`db/erd.png`에 그려진 13개 테이블(원본 4개 + 파생 5개 + 사용자 1개 + 서빙/운영 3개)을 컬럼 단위로 설명한다. TiDB(MySQL 호환) 기준이며, `db/schema.sql`과 1:1로 대응한다.

실제 파이프라인(`db/etl/`, `features/`, `models/ml/`)이 만드는 CSV 컬럼과 정확히 맞춰서 작성했다 — 예전 초안에 있던 "구버전 837개/신버전 247개 업종코드 매핑 필요", "closure_labels 별도 테이블" 같은 내용은 실제 데이터 검증 후 더 이상 유효하지 않아 반영하지 않았다.

---

## 1. 원본 데이터 기반 테이블

### `stores` — 상가업소 마스터

6개 스냅샷 전체에 걸쳐 **하나의 매장을 대표하는 마스터 행**. `store_snapshots`를 store_id로 집계해서 만든다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `store_id` | VARCHAR, PK | 상가업소번호. 스냅샷 내에서 100% 유일함을 실제 데이터로 검증 완료. |
| `current_industry_code` | VARCHAR, FK → industries.industry_code | 마지막 관측 시점(`last_seen_snapshot`) 기준 업종. |
| `dong_code` | VARCHAR, FK → administrative_dongs.dong_code | 마지막 관측 시점 기준 행정동. |
| `first_seen_snapshot` | VARCHAR(6) | 처음 관측된 스냅샷('YYYYMM'). |
| `last_seen_snapshot` | VARCHAR(6) | 마지막으로 관측된 스냅샷. |
| `n_snapshots_observed` | SMALLINT | 총 몇 번 관측됐는지. |
| `is_closed` | BOOLEAN | `last_seen_snapshot`이 마지막 스냅샷(202606)이 아니면 True — 최종 폐업 판정. |
| `had_temporary_gap` | BOOLEAN | 관측 구간 중간에 한 번 이상 빠졌다가 다시 나타난 적 있는지 (데이터 품질 플래그, 전체의 약 1.8%). |

### `store_snapshots` — 스냅샷별 상태 (패널 데이터의 본체)

6개 스냅샷 각각에서 관측된 매장의 상태를 그대로 저장하는 long format 테이블. 폐업 라벨링, 업종전환 탐지, 상호명 키워드 트렌드 계산이 전부 이 테이블에서 출발한다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `snapshot_id` | BIGINT, PK, AUTO_INCREMENT | 이 테이블만의 surrogate key. |
| `store_id` | VARCHAR, FK → stores.store_id | |
| `snapshot_date` | VARCHAR(6) | 202312, 202406, 202412, 202506, 202512, 202606 중 하나. |
| `industry_code` | VARCHAR, FK → industries.industry_code | 해당 스냅샷 시점의 업종(소분류). 6개 스냅샷 전부 동일한 247개 코드 체계를 쓰는 것을 검증 완료해서, 원본 코드 보존용 별도 컬럼은 두지 않았다. |
| `dong_code` | VARCHAR, FK → administrative_dongs.dong_code | 해당 스냅샷 시점의 행정동. 매장이 이전하지 않는 한 스냅샷마다 동일해야 하지만, 시점별로 그대로 저장한다. |
| `store_name` | VARCHAR(200) | 상호명. `trend_keywords` 계산의 원재료. |
| `floor_category` | VARCHAR(10) | 원본 층정보를 5개로 단순화: `1층`/`2층이상`/`지하`/`기타`(4자리 이상 코드 등 애매한 값)/`결측`. 실제 검증 결과 **결측 카테고리의 폐업률(12.4%)이 1층(9.3%)보다 뚜렷하게 높게 나와서**, "층정보를 기재하지 않은 매장"이라는 사실 자체가 유의미한 신호로 확인됐다. 모델에 추가한 결과 ROC-AUC 0.721→0.728, PR-AUC 0.300→0.317로 개선 — 지금까지 시도한 피처 중 유일하게 확실한 개선 효과가 있었다. |
| `lng`, `lat` | DECIMAL(10,7) | 좌표. |
| `is_closed_next` | BOOLEAN | 다음 스냅샷에서 이 매장이 사라졌는지. |
| `transitioned_next` | BOOLEAN | 다음 스냅샷으로 갈 때 업종(소분류)이 바뀌었는지. |
| `label_available` | BOOLEAN | 마지막 스냅샷(202606)만 FALSE — 다음 시점이 없어 라벨을 매길 수 없다는 뜻(서빙 전용). |

**설계 근거**: `stores`(마스터)와 `store_snapshots`(이력)을 분리해서, "이 매장이 폐업했는가"라는 마스터 레벨 질문과 "이 시점에 상태가 어땠는가"라는 이력 레벨 질문을 깔끔하게 나눴다.

### `industries` — 업종 분류 마스터

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `industry_code` | VARCHAR, PK | 업종 소분류 코드 (247개). |
| `industry_name` | VARCHAR(100) | 소분류명. |
| `industry_jung_code` | VARCHAR | 중분류 코드 (75개). |
| `industry_jung_name` | VARCHAR(100) | 중분류명. |
| `industry_dae_code` | VARCHAR | 대분류 코드 (10개). |
| `custom_group` | VARCHAR(50) | 대분류명을 그대로 채택한 커스텀 그룹(10개: 음식/소매/과학·기술/수리·개인/교육/부동산/시설관리·임대/예술·스포츠/보건의료/숙박). |

**참고**: 실제 6개 스냅샷 CSV를 전부 확인한 결과 처음부터 끝까지 동일한 소분류 247개 코드 체계를 쓰고 있어서, 예전에 우려했던 "구버전/신버전 코드 매핑" 문제는 없었다. 별도 `code_version` 컬럼이나 복합키는 불필요하다.

**모델링 스코프 참고**: 실제 폐업 예측 모델은 `custom_group`이 '과학·기술', '부동산', '시설관리·임대'인 업종은 제외한 소비자 대면 9개 업종군만 사용한다(이 세 그룹은 폐업률이 전체 평균의 절반 수준으로 이질적이고, 외부 매출 데이터에도 커버리지가 없었음). 이 제외는 `industries` 테이블이 아니라 `models/ml/01_build_modeling_dataset.py`에서 모델링 시점에만 적용되며, DB에는 전체 업종이 그대로 저장된다(업종전환 추천 등 다른 기능에서는 전체 업종이 필요하기 때문).

## 2. 파생 피처 테이블

### `population_features` — 생활인구

생활인구 3종(내국인/외국인장기/외국인단기) CSV를 행정동 단위로 평균한 결과. 실제로는 2026년 7월 한 달치(31일×24시간대)를 평균했다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `dong_code` | VARCHAR, PK/FK → administrative_dongs.dong_code | |
| `korean_pop` | DECIMAL(12,4) | 내국인 생활인구 평균. |
| `foreign_long_pop` | DECIMAL(12,4) | 외국인 장기체류 생활인구 평균. |
| `foreign_short_pop` | DECIMAL(12,4) | 외국인 단기체류 생활인구 평균. |
| `total_pop_avg` | DECIMAL(12,4) | 위 세 값의 합. |
| `foreign_short_ratio` | DECIMAL(6,5) | 단기외국인 비율. |
| `tourist_zone_candidate` | BOOLEAN | 위 비율 상위 10%면 True (관광특구 후보, 임계값은 팀에서 조정 가능). |

**검증**: 단기외국인 비율 1위가 명동(중구)으로 나와서 실제 관광특구와 일치함을 확인했다.

### `spatial_density_features` — 반경 내 밀도 피처

BallTree(haversine)로 계산한 공간 밀도 피처 4종.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `store_id` | VARCHAR, PK/FK → stores.store_id | |
| `snapshot_date` | VARCHAR(6), PK | |
| `same_industry_count_300m` | INT | 반경 300m 내 동일업종(소분류 기준) 매장 수. 기존점주 앱에서는 경쟁 리스크로, 예비창업자 앱에서는 추천도로 재사용. |
| `total_count_300m` | INT | 반경 300m 내 전체 업종 매장 수 (상권 자체의 붐비는 정도). |
| `nearest_same_industry_distance_m` | DECIMAL(10,3), NULL 허용 | 가장 가까운 동일업종 매장까지 실제 거리(m). 해당 스냅샷에서 동일업종이 자기 자신뿐이면 NULL. |
| `dong_industry_count` | INT | 반경이 아니라 행정동 전체 범위 기준 동일업종 매장 수. |
| `coord_cluster_size` | INT | 반경 20m 이내로 서로 연결된 매장들을 DBSCAN(`min_samples=1`)으로 하나의 클러스터(같은 건물/복합상가로 추정)로 묶어, 그 안의 유니크 매장 수를 센다. 좌표를 정확히 일치시켜(exact match) 묶으면 스냅샷마다 지오코딩이 미세하게 달라져(실측 1~2m 차이) 같은 건물이 다른 그룹으로 쪼개지는 문제가 있어서, 정확한 일치 대신 반경 기반 클러스터링을 쓴다. 실제 검증: 송파구의 한 좌표에 883개의 서로 다른 매장(대형 복합상가로 추정, 의류/신발/화장품/카페 등 전형적인 몰 입점 업종 구성)이 몰려있는 걸 발견해 이 피처를 추가하게 됨. |

### `trend_keywords` — 상호명 키워드 트렌드

"지금 뜨는 사업" 탐지 기능의 데이터 원천. 더미 데이터 없이 100% 실제 상호명 데이터로 계산한다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `keyword` | VARCHAR(50), PK | 예: 탕후루, 버터, 인형뽑기 등 (팀에서 자유롭게 추가/교체 가능). |
| `snapshot_date` | VARCHAR(6), PK | |
| `store_count` | INT | 해당 시점 상호명에 이 키워드가 포함된 매장 수. |
| `growth_rate` | DECIMAL(8,4), NULL 허용 | (최신 스냅샷 - 최초 스냅샷) / 최초 스냅샷. 최초값이 0이면 NULL. |

**주의**: 실제 산출물(`trend_keywords.csv`)은 keyword × snapshot_date를 컬럼으로 펼친 와이드 포맷이라, DB 적재 시 위 롱 포맷으로 pivot해야 한다.

**실제 결과 예시**: 인형뽑기 +184%, 요거트 +80%, 무인매장 +57% 상승. 탕후루는 이미 정점 지나 -89.6% 하락 — 더미 데이터가 아니라 실데이터라서 나올 수 있었던 결과.

### `industry_transitions` — 업종전환 이력

같은 매장(store_id)에서 업종이 바뀐 이벤트를 기록.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `transition_id` | BIGINT, PK, AUTO_INCREMENT | |
| `store_id` | VARCHAR, FK → stores.store_id | |
| `from_snapshot`, `to_snapshot` | VARCHAR(6) | 전환이 관측된 스냅샷 구간. |
| `from_industry_code`, `to_industry_code` | VARCHAR, FK → industries.industry_code | 전환 전/후 업종. |

**주의**: 실제 데이터에서 전환 건수가 스냅샷 구간마다 들쭉날쭉했다 — 한 구간(202406→202412)에 전체 전환의 97%가 몰려있고 나머지 구간은 0건에 가까웠다. 소상공인시장진흥공단이 업종분류를 특정 시점에만 일괄 재정비하는 것으로 보인다.

### `industry_survival_stats` — 업종별 전환 생존율 집계

`industry_transitions`를 (from, to) 조합별로 집계한 결과.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `from_industry_code`, `to_industry_code` | VARCHAR, PK/FK → industries.industry_code | |
| `sample_size` | INT | 이 조합의 관측 건수. |
| `survival_rate` | DECIMAL(6,5) | 전환 후 다음 스냅샷까지 생존한 비율. |

**한계**: "생존"의 기준이 전환 직후 다음 스냅샷까지만이라 관측 기간이 짧다(단기 생존 프록시). 표본이 적은 조합은 `sample_size`로 걸러써야 한다.

## 3. 사용자 테이블

### `users` — 로그인/세션용 계정

3개 사용자 유형을 하나의 테이블에서 `user_type`으로 구분한다. 정식 회원가입 시스템이 아니라 데모/발표용 간이 로그인이지만, 세션에 저장할 대상이 필요하므로 최소한의 테이블을 둔다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `user_id` | VARCHAR, PK | |
| `user_type` | ENUM('owner','founder','admin') | |
| `store_id` | VARCHAR, FK → stores.store_id, NULL 허용 | `user_type='owner'`일 때만 값 존재. 예비창업자는 아직 매장이 없어 NULL. |
| `login_id` | VARCHAR(50), UNIQUE | 로그인 시 입력 값. |
| `password_hash` | VARCHAR(255) | 데모 단계에서는 결정적 값으로 채울 수 있지만, **실제 서비스라면 반드시 bcrypt 등 진짜 해시로 교체해야 한다.** |
| `created_at` | DATETIME | |

## 4. 서빙/운영 테이블

### `models` — 모델 레지스트리

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `model_id` | VARCHAR, PK | |
| `model_name`, `version` | VARCHAR | |
| `model_type` | ENUM('ML','DL') | |
| `accuracy`, `precision_score`, `recall_score`, `f1_score`, `roc_auc` | DECIMAL(6,5) | `PRECISION`이 SQL 예약어라 컬럼명에 `_score`를 붙였다. |
| `trained_at` | DATETIME | |
| `is_production` | BOOLEAN | 현재 앱이 실제로 서빙에 쓰는 모델인지. |

**참고**: 실제 검증된 베이스라인은 LightGBM, ROC-AUC 0.721, PR-AUC 0.300 (과학·기술/부동산/시설관리·임대 제외, 188만 행 기준).

### `predictions` — 예측 로그 (기존점주 위험도 + 예비창업자 조회 통합)

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `prediction_id` | BIGINT, PK, AUTO_INCREMENT | |
| `model_id` | VARCHAR, FK → models.model_id | |
| `user_id` | VARCHAR, FK → users.user_id, NULL 허용 | 익명 조회 허용 시 NULL. |
| `query_type` | ENUM('existing_store','new_location') | |
| `store_id` | VARCHAR, FK → stores.store_id, NULL 허용 | `query_type='existing_store'`일 때만. |
| `query_lat`, `query_lng` | DECIMAL(10,7), NULL 허용 | `query_type='new_location'`일 때만. |
| `industry_code` | VARCHAR, FK → industries.industry_code | |
| `score` | DECIMAL(6,5) | |
| `shap_top_features` | JSON, NULL 허용 | SHAP 상위 기여 피처 목록(예: `[{"feature":"store_age_months","shap_value":-0.12,"feature_value":6}, ...]`). 기존점주 앱의 "왜 이 점수가 나왔는지" 설명 화면에 직접 쓰인다. |
| `created_at` | DATETIME | |

**성능 참고**: SHAP 값을, 특히 MLP에 쓰는 KernelExplainer는 요청마다 실시간 계산하기엔 비용이 크다. 한 번 계산한 결과를 `shap_top_features`에 캐싱해두고, 같은 조건(store_id + model_id)으로 다시 조회할 때는 재계산 없이 재사용하는 걸 권장한다.

**주의**: `store_id`와 `query_lat`/`query_lng`가 상호 배타적인 nullable 구조라, `query_type`에 따라 올바른 필드만 채우도록 하는 검증은 애플리케이션 레벨에서 해야 한다.

## 전체 관계 요약

- `users` → `stores` : 1:1 (owner 계정만)
- `users` → `predictions`, `support_actions` : 1:N
- `stores` → `store_snapshots`, `spatial_density_features`, `industry_transitions`, `predictions`, `support_actions` : 1:N
- `stores` → `administrative_dongs` : N:1
- `store_snapshots` → `administrative_dongs` : N:1
- `industries` → `store_snapshots`, `industry_transitions`(from/to 양쪽), `industry_survival_stats`(from/to 양쪽), `predictions` : 1:N
- `administrative_dongs` → `population_features` : 1:N
- `models` → `predictions` : 1:N
- `trend_keywords` : 독립 테이블 (조인 관계 없음)
