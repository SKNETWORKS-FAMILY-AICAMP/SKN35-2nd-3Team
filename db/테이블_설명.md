# DB 테이블 상세 설명

`db/erd.png`에 그려진 15개 테이블(원본 4개 + 파생 6개 + 서빙/운영 4개 + 사용자 1개)을 컬럼 단위로 설명한다. TiDB(MySQL 호환) 기준으로 작성했다.

---

## 1. 원본 데이터 기반 테이블

### `stores` — 상가업소 마스터

6개 스냅샷 전체에 걸쳐 **하나의 매장을 대표하는 마스터 행**. 상가업소번호를 기준으로 그 매장이 처음 관측된 시점, 현재(가장 최근 스냅샷 기준) 업종, 위치를 담는다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `store_id` | VARCHAR, PK | 원본 데이터의 상가업소번호. **주의**: Bank Churn 트랙에서 `CustomerId`가 유일하지 않았던 사례가 있었으므로, 이 프로젝트도 실제 6개 CSV를 확인해서 상가업소번호가 정말 유일한 식별자인지 먼저 검증해야 한다. 유일하지 않다면 별도 surrogate key를 만들어야 한다. |
| `current_industry_code` | VARCHAR, FK → industries.industry_code | 가장 최근 스냅샷(202606 또는 폐업 직전 마지막 관측치) 기준 업종. 업종전환 이력이 있는 매장은 이 값이 최초 업종과 다를 수 있다. |
| `dong_code` | VARCHAR, FK → administrative_dongs.dong_code | 생활인구 데이터와 조인하기 위한 행정동 코드. 좌표(위경도)를 행정동 경계와 공간 조인(spatial join)해서 채운다. |
| `first_seen_snapshot` | DATE | 이 매장이 처음 관측된 스냅샷 날짜. 개업 시점의 근사치로 쓸 수 있다(단, 202312 스냅샷에 이미 존재하는 매장은 "그 이전부터 있었다"는 뜻이지 "202312에 개업했다"는 뜻이 아니므로 해석에 주의). |

### `store_snapshots` — 스냅샷별 상태 (패널 데이터의 본체)

6개 스냅샷 각각에서 관측된 매장의 상태를 그대로 저장하는 **long format 테이블**. 폐업 라벨링(diff 비교), 업종전환 탐지, 상호명 키워드 트렌드 계산이 전부 이 테이블에서 출발한다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `snapshot_id` | BIGINT, PK, AUTO_INCREMENT | 이 테이블만의 surrogate key. |
| `store_id` | VARCHAR, FK → stores.store_id | 어느 매장의 스냅샷인지. |
| `snapshot_date` | DATE | 202312, 202406, 202412, 202506, 202512, 202606 중 하나. |
| `raw_industry_code` | VARCHAR | 원본 CSV에 찍혀 있던 업종 코드 **그대로** (구버전 837개 또는 신버전 247개 체계 중 하나, 스냅샷 시점에 따라 다름). 가공하지 않은 원본값을 보존해서, 나중에 매핑 로직에 문제가 생겼을 때 원본으로 되돌아갈 수 있게 한다. |
| `store_name` | VARCHAR | 상호명. `trend_keywords` 계산의 원재료. |
| `lat`, `lng` | DECIMAL | 해당 스냅샷 시점의 좌표. 이론적으로 매장이 이전하지 않는 한 스냅샷마다 동일해야 하지만, 좌표 보정이 스냅샷마다 달라질 수 있어 매번 저장한다. |

**설계 근거**: `stores`(마스터)와 `store_snapshots`(이력)을 분리한 이유는, "이 매장이 폐업했는가"라는 마스터 레벨의 질문과 "이 시점에 업종이 무엇이었는가"라는 이력 레벨의 질문을 섞으면 폐업 라벨링 로직이 지저분해지기 때문이다. `closure_labels`는 이 `store_snapshots`를 스냅샷 순서대로 diff해서 만든 **파생 결과**다.

### `industries` — 업종 분류 마스터

구버전(837개 카테고리)과 신버전(247개 카테고리) 업종 코드를, 업종명 텍스트를 브릿지로 삼아 8~12개의 커스텀 그룹으로 통합한 매핑 테이블.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `industry_code` | VARCHAR, PK | 원본 업종 코드 (구버전/신버전 코드가 섞여 있을 수 있음 — 코드 체계가 다르므로 `code_version` 컬럼으로 구분 필요, 아래 참고). |
| `industry_name` | VARCHAR | 원본 업종명 텍스트. 코드 체계가 바뀌어도 업종명은 상대적으로 안정적이라, 이 텍스트를 기준으로 그룹핑했다. |
| `custom_group` | VARCHAR | 8~12개로 통합한 커스텀 그룹명 (예: "카페/디저트", "음식점", "소매" 등, 팀에서 최종 확정 필요). |

**주의**: 이 테이블은 `industry_code` 하나를 PK로 잡았지만, 실제로는 구버전 코드와 신버전 코드가 서로 다른 값 체계이기 때문에 `code_version`(구/신) 컬럼을 추가해서 `(industry_code, code_version)` 복합키로 가는 게 더 안전할 수 있다 — 실제 CSV를 열어보고 코드 값이 겹치는지 확인 후 확정할 것.

### `closure_labels` — 폐업 라벨

`store_snapshots`를 시점 순으로 비교해서 만든 폐업 여부 판정 결과.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `store_id` | VARCHAR, PK, FK → stores.store_id | 매장당 1행. |
| `is_closed` | BOOLEAN | 이후 스냅샷에서 더 이상 관측되지 않으면 True. |
| `closure_snapshot_date` | DATE, NULLABLE | 마지막으로 관측된 스냅샷 다음 시점(폐업으로 판정된 시점). 폐업하지 않은 매장은 NULL. |

**설계 근거**: 학습에는 2022~2025 스냅샷 행을 쓰고 2026 스냅샷(202606)은 미래 비교가 불가능해서 라벨을 매길 수 없으므로 서빙 전용으로만 쓴다는 원칙이 이 테이블에 그대로 반영된다 — 202606에만 존재하는 매장은 `is_closed`가 아직 판정 불가 상태(NULL 또는 별도 플래그)로 둬야 한다.

### `administrative_dongs` — 행정동 마스터

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `dong_code` | VARCHAR, PK | 행정동 코드. |
| `dong_name` | VARCHAR | 행정동 이름 (예: 역삼1동). |
| `gu_name` | VARCHAR | 구 이름 (예: 강남구). EDA에서 확인된 "강남구 집중도 높음" 같은 분석에 쓰인다. |

## 2. 파생 피처 테이블

### `population_features` — 생활인구

최신 시점 1개 스냅샷만 사용하기로 확정된 생활인구 데이터.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `dong_code` | VARCHAR, PK, FK → administrative_dongs.dong_code | 행정동 단위 집계. |
| `korean_pop` | INT | 내국인 생활인구. |
| `foreign_long_pop` | INT | 외국인 장기체류 생활인구. 관광특구 플래그를 만들 때 이 값과 `foreign_short_pop`의 비율을 쓸 수 있다. |
| `foreign_short_pop` | INT | 외국인 단기체류 생활인구. |

시계열이 아니라 스냅샷 1개이므로 `snapshot_date`를 별도 컬럼으로 두지 않고 문서(README)에 "최신 시점 기준"이라고 명시하는 편이 테이블을 단순하게 유지한다. (팀에서 원하면 `snapshot_date` 컬럼을 추가해 향후 갱신에 대비할 수도 있다.)

### `spatial_density_features` — 반경 내 경쟁밀도

BallTree(haversine)로 계산한, 반경 300m 안의 **동일 업종** 매장 수.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `store_id` | VARCHAR, PK, FK → stores.store_id | |
| `snapshot_date` | DATE, PK | 스냅샷마다 주변 매장 구성이 바뀌므로 시점별로 값이 다르다. |
| `same_industry_count_300m` | INT | 반경 300m 안에 있는 동일 업종 매장 수. 기존점주 앱에서는 "경쟁 리스크" 피처로, 예비창업자 앱에서는 "추천도" 피처로 이 값 하나를 그대로 재사용한다. |

### `trend_keywords` — 상호명 키워드 트렌드

"지금 뜨는 사업" 탐지 기능의 데이터 원천. 더미 데이터 없이 100% 실제 상호명 데이터로만 계산한다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `keyword` | VARCHAR, PK | 예: "탕후루", "버터떡". |
| `snapshot_date` | DATE, PK | 6개 스냅샷 중 하나. |
| `store_count` | INT | 해당 시점에 상호명에 이 키워드가 포함된 매장 수. |
| `growth_rate` | FLOAT | 직전 스냅샷 대비(혹은 최초 스냅샷 대비) 증가율. 관리자 대시보드의 "뜨는 사업" 화면이 이 컬럼을 정렬해서 보여준다. |

이 테이블은 다른 테이블과 조인 관계가 없는 독립 집계 테이블이라 ERD에서도 따로 떨어져 있다 — `store_snapshots`에서 배치로 집계해 채워 넣는 방식이라 실시간 FK 관계가 필요 없다.

### `industry_transitions` — 업종전환 이력

같은 매장(같은 위치)에서 업종이 바뀐 이벤트를 기록.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `transition_id` | BIGINT, PK, AUTO_INCREMENT | |
| `store_id` | VARCHAR, FK → stores.store_id | |
| `from_industry_code` | VARCHAR, FK → industries.industry_code | 전환 전 업종. |
| `to_industry_code` | VARCHAR, FK → industries.industry_code | 전환 후 업종. |
| `transition_date` | DATE | 전환이 관측된 스냅샷 시점(전-후 스냅샷 사이). |
| `survived` | BOOLEAN | 전환 이후 다음 스냅샷들에서 계속 생존했는지 여부. |

**주의**: 이 테이블은 "폐업"과 "업종전환"을 구분하는 로직에 직접 의존한다 — 같은 `store_id`가 사라지지 않고 `raw_industry_code`만 바뀌면 전환, `store_id` 자체가 사라지면 폐업으로 판정해야 하며, 이 판정 로직이 잘못되면 `closure_labels`와 `industry_transitions` 양쪽 다 오염된다.

### `industry_survival_stats` — 업종별 전환 생존율 집계

`industry_transitions`를 `(from, to)` 조합별로 집계한 결과. 업종전환 추천 기능의 근거 데이터.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `from_industry_code` | VARCHAR, PK, FK → industries.industry_code | |
| `to_industry_code` | VARCHAR, PK, FK → industries.industry_code | |
| `survival_rate` | FLOAT | 이 업종에서 저 업종으로 전환했을 때, 이후 관측 기간 동안 생존한 비율. |
| (선택) `sample_size` | INT | 이 조합의 관측 건수. 표본이 너무 적은 조합은 추천에서 걸러내는 데 쓴다 — 조합 수가 많아지면(업종그룹 10개 기준 최대 90개 조합) 일부는 표본이 매우 적을 수 있으므로 반드시 확인 필요. |

### `serving_features` — 모델 서빙용 최종 피처

위의 모든 파생 피처를 합쳐서 모델에 바로 넣을 수 있게 만든 최신 시점 스냅샷.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `store_id` | VARCHAR, PK, FK → stores.store_id | |
| `feature_snapshot_date` | DATE | 이 피처들이 어느 시점 기준으로 계산됐는지. |
| (실제로는 다수 컬럼) | — | `spatial_density_features`, `population_features`, 업종그룹 원-핫 등을 전부 조인해서 만든 넓은(wide) 테이블. 컬럼이 많아질 걸 감안해 여기서는 대표 컬럼만 표기했고, 실제 스키마는 피처 확정 후 별도로 작성한다. |

## 3. 서빙/운영 테이블

### `models` — 모델 레지스트리

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `model_id` | VARCHAR, PK | |
| `model_name` | VARCHAR | 예: "lightgbm_v2". |
| `version` | VARCHAR | |
| `model_type` | ENUM('ML','DL') | Logistic Regression/RF/LightGBM은 ML, MLP는 DL. |
| `accuracy`, `recall`, `f1`, `roc_auc` | FLOAT | 평가 지표. |
| `trained_at` | DATETIME | |
| `is_production` | BOOLEAN | 현재 앱이 실제로 서빙에 쓰는 모델인지 표시. |

### `predictions` — 예측 로그 (기존점주 위험도 + 예비창업자 조회 통합)

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `prediction_id` | BIGINT, PK, AUTO_INCREMENT | |
| `model_id` | VARCHAR, FK → models.model_id | 어떤 모델이 이 예측을 만들었는지. |
| `user_id` | VARCHAR, FK → users.user_id, NULLABLE | 누가 이 조회를 요청했는지 (익명 조회를 허용할 경우 NULL 가능). |
| `query_type` | ENUM('existing_store','new_location') | 기존점주 위험도 조회인지, 예비창업자의 위치+업종 조회인지 구분하는 핵심 컬럼. |
| `store_id` | VARCHAR, FK → stores.store_id, NULLABLE | `query_type='existing_store'`일 때만 값이 있음. |
| `query_lat`, `query_lng` | DECIMAL, NULLABLE | `query_type='new_location'`일 때만 값이 있음 — 예비창업자가 지도에서 찍은 위치. |
| `industry_code` | VARCHAR, FK → industries.industry_code | 기존점주는 현재 업종, 예비창업자는 검토 중인 업종. |
| `score` | FLOAT | 위험도 또는 추천도 점수 (0~100 또는 0~1, 팀에서 스케일 확정 필요). |
| `created_at` | DATETIME | |

**주의**: `store_id`와 `query_lat`/`query_lng`가 서로 배타적(mutually exclusive)인 nullable 컬럼 구조라, 애플리케이션 레벨에서 `query_type`에 따라 올바른 필드만 채우도록 하는 검증 로직이 반드시 필요하다. DB 레벨에서 강제하려면 CHECK 제약을 추가하거나, 아예 두 하위 테이블로 쪼개는 것도 여전히 옵션으로 남겨둔다(2주 안에 시간이 부족하면 통합 유지, 여유 있으면 분리 고려).

### `support_actions` — 관리자 개입 로그 (closed-loop)

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `action_id` | BIGINT, PK, AUTO_INCREMENT | |
| `store_id` | VARCHAR, FK → stores.store_id | 어느 매장에 대한 조치인지. |
| `admin_user_id` | VARCHAR, FK → users.user_id | 어떤 관리자가 조치했는지. |
| `action_type` | VARCHAR | 예: "전화상담", "지원금 안내", "현장방문". |
| `action_date` | DATE | |
| (선택) `follow_up_closure_status` | BOOLEAN, NULLABLE | 조치 이후 실제로 폐업했는지 추적 — "개입 후 폐업률 추적"이라는 closed-loop 설계 목표를 이 컬럼이 직접 뒷받침한다. |

## 4. 사용자 테이블

### `users` — 로그인/세션용 계정

3개 사용자 유형을 하나의 테이블에서 `user_type`으로 구분한다. 정식 회원가입 시스템이 아니라 데모/발표용 간이 로그인이지만, 세션에 저장할 대상이 필요하므로 최소한의 테이블은 둔다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `user_id` | VARCHAR, PK | |
| `user_type` | ENUM('owner','founder','admin') | |
| `store_id` | VARCHAR, FK → stores.store_id, NULLABLE | `user_type='owner'`일 때만 값이 있음. 예비창업자는 아직 매장이 없으므로 NULL. |
| `login_id` | VARCHAR, UNIQUE | 로그인 시 입력하는 값. owner는 store_id 기반, admin은 고정값("admin") 등. |
| `password_hash` | VARCHAR | 데모 단계에서는 store_id를 시드로 한 결정적 값으로 채울 수 있지만(Bank Churn 트랙 3.1 참고), **실제 서비스라면 반드시 bcrypt 등 진짜 해시로 교체해야 한다**는 점을 결과서에 명시할 것. |
| `created_at` | DATETIME | |

**설계 근거**: 예비창업자는 "회원가입"이 아니라 그냥 즉석에서 세션이 만들어지는 형태(비회원 게스트)로 갈 수도 있는데, 그 경우에도 조회 로그(`predictions.user_id`)를 남기려면 최소한 임시 게스트 user 행을 하나 만들어서 session_id처럼 쓰는 방법이 있다 — 이 부분은 실제 구현 단계에서 팀이 정할 세부사항으로 남겨둔다.

## 전체 관계 요약

- `users` → `stores` : 1:1 (owner 계정만)
- `users` → `predictions`, `support_actions` : 1:N
- `stores` → `store_snapshots`, `spatial_density_features`, `industry_transitions`, `predictions`, `support_actions` : 1:N
- `stores` → `closure_labels`, `serving_features` : 1:1
- `stores` → `administrative_dongs` : N:1
- `industries` → `store_snapshots`, `industry_transitions`(from/to 양쪽), `industry_survival_stats`(from/to 양쪽), `predictions` : 1:N
- `administrative_dongs` → `population_features` : 1:N
- `models` → `predictions` : 1:N
- `trend_keywords` : 독립 테이블 (조인 관계 없음)

## 아직 확정 안 된 것 (팀 논의 필요)
- `store_id`(상가업소번호)가 6개 CSV 전체에서 정말 유일한지 검증
- `industries.industry_code`를 구/신버전 통합 단일 키로 쓸지, `code_version`을 추가해 복합키로 갈지
- `predictions` 테이블을 지금처럼 통합 유지할지, 나중에 두 테이블로 분리할지
- `serving_features`의 실제 전체 컬럼 목록 (피처 확정 후 작성)
- `industry_survival_stats`에 `sample_size`(표본 크기) 컬럼을 넣어서 표본 부족 조합을 걸러낼지
