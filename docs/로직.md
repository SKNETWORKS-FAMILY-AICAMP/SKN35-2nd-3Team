# 메인 화면 UI 동작 로직 정리

작성일: 2026-08-26

지금까지 확정된 내용(로그인 3분기, 생존점수 변환, 지도는 히트맵, 핫동네는 자체 지수)을 바탕으로 화면이 실제로 어떻게 동작해야 하는지 로직으로 정리. UI 목업(4개 화면)과 [[seoul-biz-schema-ui-mapping]] 문서와 함께 참고.

## 1. 진입 시 라우팅

```
로그인 안 함           -> 메인(GUEST)
로그인 + user_type='founder' (store_id 없음) -> 메인(NEW_MEMBER)
로그인 + user_type='owner'   (store_id 있음) -> 메인(OWNER, store_id=내 가게)
로그인 + user_type='admin'                    -> 관리자 대시보드 (메인 화면과 별도, 화면 설계는 추후)
```

## 2. 공통 레이아웃 로직 (좌: 지도 / 우: 패널)

지도는 4가지 상태 모두에서 항상 존재하고, **내용만** 상태별로 달라짐. 우측 패널은 상태별로 완전히 다른 콘텐츠.

| 상태 | 지도 | 우측 패널 |
|---|---|---|
| GUEST | 서울 전체 히트맵(전체 매장 생존점수 가중) | 지금 뜨는 동네 카드 + 로그인 유도 배너 |
| NEW_MEMBER | GUEST와 동일 | GUEST와 동일 + 상단 온보딩 배너("가게 등록하면...") |
| OWNER | 내 가게 dong_code로 센터/줌 이동, 마커 표시, 나머지는 옅게 | 유동인구(시점값) 카드 + 내 업종 생존점수 게이지 + 업종 전환 추천 리스트 |
| (공통) 지도에서 동/구 클릭 | 그 지역 하이라이트, 지도 자체는 안 바뀜 | 지역 상세 패널로 전환(업종별 랭킹 등) |

**내 가게 포커스(OWNER)는 별도 계산 없이 바로 가능** — `stores`에서 내 store_id의 최신 lat/lng·dong_code를 조회해서 `folium.Map(location=[lat,lng], zoom_start=15~16)`으로 초기화하고 마커만 찍으면 끝. 클릭 판별 로직(A-1)도 필요 없음, 내 가게 좌표는 이미 알고 있으니까.

## 3. 생존점수 계산 로직

```
predictions.score = 모델이 뱉는 폐업확률(p, 0~1)로 가정
survival_score = round((1 - p) * 100)

등급:
  survival_score >= 80      -> 우수 (good, 초록)
  65 <= survival_score < 80 -> 양호 (warning, 노랑)
  45 <= survival_score < 65 -> 주의 (serious, 주황)
  survival_score < 45       -> 위험 (critical, 빨강)
```

✅ **2026-08-26 확인**: 팀원 전처리 기록으로 실제 모델 구조 확인됨 — LightGBM, 타깃 `is_closed_next`(폐업확률), 최종 검증 ROC-AUC ≈ 0.728~0.748(버전별), F1 ≈ 0.28. `predictions.score`가 폐업확률이라는 가정이 맞았음 → 위 `생존점수 = (1-p)×100` 변환 그대로 유효.

⚠️ **UI 문구에 반영할 것**: ROC-AUC 0.75 전후, F1 0.28 전후는 "적당히 쓸만한" 수준이지 확정적인 예측이 아님. 점수 카드에 "이 점수는 예측 참고용이며 실제와 다를 수 있어요" 같은 짧은 신뢰도 문구를 넣는 걸 권장 — 특히 소상공인 대상 서비스라 과신하게 만들면 안 됨.

**내 업종 점수 조회 (OWNER)**
```
predictions WHERE query_type='existing_store' AND store_id=내 store_id
  중 가장 최근 것 1건 조회
없으면 -> 그 자리에서 모델 호출 -> predictions에 INSERT (다음부터는 캐시로 재사용)
```

### 3-1. (제안) 점수 근거 카드 — `shap_top_features` 활용

전처리 로그에서 확인된 실제 피처들(`industry_historical_rate`, `dong_historical_rate`, `coord_cluster_size`, `competition_per_capita_300m`, 생활인구, `is_left_censored_age`, `is_trend_keyword_match`, `floor_category` 등)이 꽤 설명력 있는 이름들이라, `predictions.shap_top_features`(JSON, 이미 스키마에 있음)를 그대로 "내 업종 점수" 카드 하단에 짧게 풀어서 보여줄 수 있음.

```
shap_top_features 예: [{"feature":"coord_cluster_size","shap_value":-0.12,"feature_value":6}, ...]
-> UI 문구로 매핑: feature명 -> 사람이 읽는 문장으로 변환하는 매핑 테이블 필요
   예) coord_cluster_size(양수 기여) -> "대형 상가/복합몰 입점 — 유리하게 작용"
       dong_historical_rate(음수 기여) -> "이 지역 평균 폐업률이 높음 — 불리하게 작용"
상위 2~3개만 노출(전부 나열하면 소상공인 입장에서 오히려 복잡함)
```

지금 목업(Existing.dc.html)의 "최근 3개월 동종 업종 신규 오픈 3건..." 같은 문장은 임의로 지어낸 것이었는데, 이 방식으로 가면 실제 SHAP 근거 기반 문장으로 교체 가능. 우선순위는 낮음(핵심 로직 먼저) — 나중에 붙여도 됨.

### 3-2. 팀원 "프로젝트 한계점" 문서 반영 — UI가 챙겨야 할 것 (2026-08-26 추가)

팀원이 정리한 모델링 한계점 문서를 보고, UI/서비스 단에서 추가로 처리해야 하는 것들:

- **모델링 제외 업종 처리 필요**: 과학·기술/부동산/시설관리·임대 업종군은 애초에 학습 대상이 아님. 지역 상세 업종 랭킹에 이 업종들이 섞여 나오면 안 되고, 목록에서 제외하거나 "예측 대상 아님"으로 명시해야 함 — 지금 로직(4번)에는 이 예외 처리가 빠져 있어서 추가 필요.
- **표본 부족 대체값 구분 표시**: `dong_industry_historical_rate`가 표본 30건 미만이면 업종 평균으로 대체되는데, 지역 상세 랭킹에서 "이 동네 실측 기반 점수"와 "업종 평균 대체 추정치"를 구분 없이 같은 숫자로 보여주면 안 됨 — 대체값인 경우 작은 배지("동네 표본 부족, 업종 평균 기준")로 구분 표시 권장.
- **업종 전환 추천에 관측기간 caveat**: `industry_survival_stats`의 생존율은 전환 후 최대 6개월(다음 스냅샷)까지만 관측한 단기 지표. "업종 전환 추천" 카드에 "6개월 내 단기 생존 기준" 같은 짧은 문구 추가 권장.
- **점수는 절대 확률이 아니라 상대 순위로 표현**: LightGBM `predict_proba` 원본 확률은 별도 calibration 검증이 안 됐고(트리 모델은 원 확률이 실제 빈도와 어긋나는 경우가 흔함), 기저 폐업률이 낮아 Precision도 구조적으로 낮음(팀원 문서 결론과 동일). 그래서 "생존점수 78점" 같은 절대 수치보다 지금 목업처럼 **"상위 18%"식 상대 순위(percentile) 병기**가 이 모델 성능 수준에 맞는 정직한 표현임 — 이미 그렇게 하고 있어서 유지하면 됨.

## 4. 지역 상세(동/구 클릭) 로직

```
클릭한 좌표 -> A-1(최근접 중심점)로 dong_code 판별
industries 테이블의 각 industry_code에 대해 (단, 모델링 제외 업종군은 제외 — 3-2 참고):
    predictions WHERE query_type='new_location' AND query_lat/lng=해당 좌표 AND industry_code=X 캐시 조회
    캐시 없으면 그 자리에서 모델 호출해서 새로 생성
survival_score로 변환 -> 내림차순 정렬 -> 랭킹 리스트로 즉시 표시 (표본 부족 대체값은 배지로 구분 — 3-2 참고)

지역 요약 카드: population_features(유동인구 시점값), spatial_density_features(경쟁 강도)
```

**"바로바로" 보여주는 게 가능한가?** 네, 두 방식을 섞으면 체감상 즉시 반응함:

- **캐시 히트(인기 동네)**: `predictions` 테이블에서 이미 계산된 값을 SELECT만 하면 되니 사실상 즉시.
- **캐시 미스(처음 클릭되는 동)**: 업종 수가 많지 않으니(전체 industries 테이블 기준) 한 업종씩 루프 돌지 말고, **industry_code 전체를 한 번에 행렬로 만들어서 LightGBM에 배치(벡터) 추론 1회로 처리** — 이러면 업종이 수십 개여도 체감상 즉시(수십~수백ms) 응답 가능. 느려지는 건 "업종별로 하나씩 순차 호출"할 때뿐.
- 처음 계산된 결과는 `predictions`에 INSERT해서 다음 방문자부터는 캐시 히트로 전환 → 인기 동네일수록 점점 더 빨라지는 구조.

## 5. "지금 뜨는 동네" 핫 지수 로직

동별로 계산(배치, 예: 매일 1회):

```
new_store_ratio  = (dong 내 최근 N개월 신규매장 수) / (dong 내 전체 매장 수)
survival_ratio   = 1 - (dong 내 폐업 매장 수 / dong 내 전체 매장 수)
growth_slope     = dong별 활성 매장 수 시계열의 최근 증가율(기울기)

각 지표를 전체 dong 기준 0~1 정규화 후:
hot_index = (new_store_ratio + survival_ratio + growth_slope) / 3   -- 초기 가중치 균등, 추후 조정

상위 4~5개 dong -> "지금 뜨는 동네" 카드
카드의 ▲n% 뱃지 = growth_slope 기반 증가율
카드의 점수 = hot_index를 0~100 스케일 또는 해당 dong 평균 survival_score (택1)
```

⚠️ 이것도 요청마다 계산하지 말고 배치 결과를 별도 캐시 테이블(예: `dong_hot_index`)에 저장해두는 걸 권장 — 기존 데이터에서 파생되는 값이라 스키마에 테이블 하나 추가하는 정도로 자연스럽게 들어감. 원하면 DDL 초안 만들어줄 수 있음.

## 6. 로그인 / 세션

- login_id + password_hash 검증 → 세션에 user_id, user_type, store_id 저장
- 비로그인 상태에서도 `predictions.user_id`는 NULL 허용 → 게스트도 지역 클릭 시 업종 랭킹 조회 가능(스키마 코멘트에 명시된 설계)
- OWNER/NEW_MEMBER 화면 우측 상단 프로필 아이콘 클릭 → MY 화면 진입 (화면 설계는 추후)

## 아직 설계 안 된 것

- 관리자 대시보드(A 화면들) — `predictions` + `support_actions`로 스키마는 준비돼 있음, 화면 설계는 다음 단계
- MY(마이페이지) 화면
- `dong_hot_index` 같은 캐시 테이블을 실제로 스키마에 추가할지 여부
- SHAP 근거 문장 매핑 테이블(3-1) — 우선순위 낮음, 여유 있을 때
- 3-2에서 추가된 예외 처리(제외 업종, 대체값 배지)의 실제 구현
